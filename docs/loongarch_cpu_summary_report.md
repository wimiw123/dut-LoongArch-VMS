# LoongArch CPU 项目总结报告

## 1. 报告概述

本项目实现的是一个面向课程实验与体系结构教学的 LoongArch 32 位 CPU 模拟器。项目既保留了基础的顺序执行模型，也扩展出了带有五级前端、动态分支预测、Tomasulo 风格动态调度和 ROB 顺序提交的高级核心模型。围绕 CPU 本体，仓库还搭建了完整的平台环境，包括总线、内存、UART、Timer、测试设备、最小运行时、程序加载器和多层测试框架，使其不仅能执行手写测试程序，也能运行由 LoongArch 交叉编译器生成的 C 程序。

从工程目标看，这个项目解决的不是“只让一条条指令跑起来”这么简单，而是把一个教学 CPU 需要的关键能力尽量完整地串联起来：一方面覆盖指令系统、异常中断、页式地址翻译、MMIO 外设等体系结构内容；另一方面覆盖构建流程、测试框架、对比口径、回归验证等工程化内容。因此，它既是一套 CPU 功能模拟器，也是一套可支撑课程实验迭代的微结构实验平台。

## 2. 工程构建与系统组成

### 2.1 工程构建方式

项目使用 CMake 构建，核心源码集中在 `src/` 和 `include/`，测试用例位于 `tests/unit/` 和 `tests/program/`。基本构建流程如下：

```bash
cmake -S . -B build
cmake --build build -j
```

构建完成后会生成：

- `build/mycpu_sim`：主模拟器入口；
- `build/program_test_runner`：程序级回归测试入口；
- `build/test_*`：18 个单元/模块测试可执行文件。

此外，项目还提供了针对 LoongArch 交叉编译链的脚本：

- `toolchain/build_c_program.sh`：将 C 程序与最小运行时编译、链接为 `build_runtime/*.bin`；
- `toolchain/run_c_tests.sh`：批量编译并运行 C 程序测试；
- `toolchain/run_c_tests_compare.sh`：compare 专用入口，用于与 PA 框架对齐后的统一测试；
- `toolchain/mycpu_sim_baseline.sh`、`toolchain/mycpu_sim_advanced.sh`：分别固定到顺序核和高级核模式。

### 2.2 平台级系统组成

整个模拟平台由以下模块组成：

- `CPU`：LoongArch 核心，负责取指、译码、执行、异常处理与性能统计；
- `Memory`：主内存，默认容量 16 MiB；
- `Bus`：统一总线，负责把物理地址访问路由到内存或 MMIO 设备；
- `Uart`：串口设备，负责将字符输出到终端；
- `Timer`：定时器设备，可产生周期性中断；
- `TestDevice`：测试专用 MMIO 设备，用于 goodtrap/badtrap 退出；
- `ProgramLoader`：负责 `.hex` 和 `.bin` 程序镜像装载；
- `SimulatorRunner`：负责一次模拟运行的搭建、执行与结果汇总。

默认平台配置如下：

- 程序入口地址：`0x1000`
- 数据段基址：`0x2000`
- 栈顶地址：`0xF000`
- 测试设备地址：`0x1FFFF000`
- 最大步数预算：`1,000,000`

这些配置让 CPU、运行时和测试程序共享统一的平台假设，降低了调试和回归测试时的耦合成本。

## 3. CPU 构建与总体设计

### 3.1 两种核心模式

当前 CPU 有两种运行模式：

- `baseline`：顺序执行解释器，强调 ISA 正确性和实现清晰度；
- `advanced`：带流水线、投机和乱序执行的高级核心，强调微结构能力。

模式通过环境变量 `LOONGARCH_CORE_MODE` 或命令行参数 `--core-mode` 切换。若未显式指定，默认进入 `advanced` 模式。

### 3.2 架构状态

CPU 内部维护了较完整的体系结构状态，主要包括：

- 32 个 32 位通用寄存器；
- 程序计数器 `PC`；
- 异常相关寄存器 `EPC`、`ESTAT`；
- 控制相关寄存器 `CRMD`、`ECFG`；
- 页目录基址寄存器 `PGDL`；
- CSR 数组；
- 浮点寄存器和 LL/SC 状态字段。

其中，浮点状态和 LL/SC 状态目前只保留了字段，尚未形成完整指令支持；而 `r0` 恒为 0 的架构约束在每次执行后都会被显式维护。

### 3.3 顺序核执行流程

`baseline` 模式对应经典的“取指-译码-执行-写回”解释执行路径。每次 `step()` 的基本过程是：

1. 检查挂起中断；
2. 依据 `PC` 取指，必要时进行地址翻译；
3. 将原始指令译码为统一的指令描述结构；
4. 执行算术、访存、分支、CSR 或异常语义；
5. 更新寄存器、`PC` 和相关状态；
6. 增加周期计数和提交计数。

这种模式结构直观，非常适合作为 ISA 验证和新指令接入的基线模型。

## 4. 指令系统支持情况

### 4.1 总体范围

根据仓库内的 `CPU_INSTRUCTION_SUPPORT.md`，当前已经实现 59 条 LoongArch 指令，覆盖课程实验常用的整数、访存、控制流和特权子集，但尚未实现浮点、LL/SC、TLB 管理和缓存管理等更复杂的扩展内容。

### 4.2 已支持指令类别

当前支持的主要指令类别如下。

| 类别 | 已支持内容 |

| 乘除法 | `MUL.W`、`MULH.W`、`MULH.WU`、`DIV.W`、`MOD.W`、`DIV.WU`、`MOD.WU` |

### 4.3 指令支持的工程意义

这套指令子集足以支撑课程中的大多数整数程序、条件分支、循环、数组访问、排序、递归和基础函数调用。项目中的 `tests_copy` 和 `my_programs_c` 目录就包含了大量基于这些指令运行的 C 程序样例，例如排序、矩阵乘法、递归、字符串处理、素数与数论程序等。

同时，项目也明确区分了“当前能跑的教学子集”和“尚未实现的完整 ISA”。这使得报告在描述能力时可以既肯定已有成果，又不过度夸大系统范围。

## 5. 流水线与动态调度实现

### 5.1 高级核心的定位

`advanced` 模式不是简单地把顺序核拆成几个阶段，而是实现了一个“前端流水化 + 后端乱序执行 + ROB 顺序提交”的混合微结构。它的重点不在宿主机速度，而在于把现代 CPU 中常见的关键机制体现出来，包括：

- 五级前端；
- 动态分支预测；
- Tomasulo 风格保留站；
- 寄存器重命名；
- ROB 顺序提交；
- 投机执行与失预测恢复；
- Load/Store 顺序检查与前递。

### 5.2 流水线阶段划分

高级核心的执行过程可以概括为以下阶段：

1. `IF`：按预测路径取指；
2. `ID`：把取回指令送入译码槽；
3. `Rename/Dispatch`：分配 ROB 和保留站，完成寄存器重命名；
4. `Issue`：从保留站中选择 ready 指令发射到功能部件；
5. `Execute/Writeback`：功能部件执行完成后将结果写回 ROB，并唤醒依赖者；
6. `Commit`：ROB 按程序顺序提交，更新架构状态。

从教科书视角看，这相当于在五级流水线基础上增加了乱序机器必须具备的提交阶段，因此已经具备了较完整的现代 CPU 微结构雏形。

### 5.3 动态调度：Tomasulo 风格实现

高级核心中的动态调度主要依赖三组结构：

- `Reservation Station`：保存等待发射的指令和源操作数状态；
- `RAT`：寄存器别名表，负责把架构寄存器映射到最新的生产者；
- `ROB`：保存投机结果并保证顺序提交。

其核心流程是：

1. 指令进入 `Rename/Dispatch` 阶段时分配一个全局顺序号 `seq`；
2. 若源寄存器的生产者尚未提交，则在保留站中记录该生产者的 tag；
3. 生产者执行完成后，通过 tag 唤醒依赖者；
4. 指令一旦 ready，就可按功能部件可用性乱序发射；
5. 即使执行完成顺序发生重排，最终仍由 ROB 按程序顺序提交。

这正是 Tomasulo 思想在教学 CPU 上的工程化实现。它不是完整复刻论文中的多发射和多广播总线设计，但已经完整体现了“重命名-等待-唤醒-乱序执行-顺序退休”的核心机制。

### 5.4 关键微结构参数

当前高级核心的几个关键参数如下：

- ROB 容量：24 项；
- 保留站容量：16 项；
- 分支预测表：128 项；
- 功能部件数量：5 类，每类 1 个实例。

功能部件包括：

- `alu`
- `muldiv`
- `mem`
- `branch`
- `system`

因此，当前核心属于“单发射乱序核”，具备 OoO 能力，但还不是 superscalar 多发射处理器。

### 5.5 Load/Store 相关优化

在访存方面，高级核心做了两类关键处理：

- 对 load 指令执行老 store 检查，避免违反内存顺序；
- 对命中相同地址的 load/store 进行前递，减少不必要的等待。

这说明项目不仅实现了抽象层面的乱序执行，还考虑了实际 OoO 处理中最容易出错的内存相关依赖问题。

## 6. 动态分支预测与投机恢复

### 6.1 分支预测机制

高级核心使用 128 项分支预测表，每项包含：

- 2-bit 饱和计数器；
- 是否存在有效目标地址；
- 最近目标地址。

预测策略具备以下特征：

- `B`、`BL`：固定预测 taken；
- `JIRL`：若历史表项中有有效目标，则直接预测到目标；
- 条件分支：基于 2-bit 饱和计数器动态判断 taken/not-taken；
- `ERTN`：不做动态预测，按顺序流处理。

### 6.2 失预测处理

当分支真实结果与预测结果不一致时，高级核心会：

- 清除更年轻的 ROB 项；
- 清除更年轻的保留站项；
- 清空前端 `if_stage` 与 `id_stage`；
- 取消更年轻的功能部件执行；
- 依据剩余 ROB 重建 RAT；
- 将 `fetch_pc` 重定向到真实下一条 PC。

这一机制保证了投机执行后的恢复正确性，也保证了异常和分支恢复后的架构状态精确可控。

## 7. 异常、中断与 MMU

### 7.1 异常与中断

项目已经实现基础异常与中断机制，包括：

- 地址错误异常；
- 非法指令异常；
- `SYSCALL`；
- `BREAK`；
- 外部中断信号处理。

异常入口采用统一向量形式：

- 异常入口地址 = `0x1C000000 + ex_code * 0x100`

进入异常后，CPU 会保存 `EPC`、更新 `ESTAT`、关闭中断使能位，并跳转到对应异常入口。`ERTN` 则负责从异常返回并恢复执行。

### 7.2 MMU 设计

当前 MMU 采用简化的两级页表结构，通过 `PGDL` 给出页目录基址。地址翻译流程如下：

1. 若 `CRMD` 中分页位未开启，则虚实地址直通；
2. 否则从虚地址中提取页目录索引、页表索引和页内偏移；
3. 读取页目录项 `PDE`，检查有效位；
4. 读取页表项 `PTE`，检查有效位；
5. 将物理页框号与页内偏移拼接为最终物理地址。

这套 MMU 虽然是教学化简版本，但已经能体现分页翻译、缺页异常和页表访问的完整路径。

### 7.3 MMU 测试结果

当前仓库中的 `test_mmu` 已验证两条关键路径：

- 映射路径：虚地址 `0x12345000` 能正确翻译到物理页，并成功取指执行；
- 缺页路径：访问未映射地址后，PC 会跳转到地址错误异常入口 `0x1C000200`。

这说明 MMU 的成功翻译和异常回退路径均已经具备可验证实现。

## 8. UART、Timer、Bus 与测试设备

### 8.1 Bus 总线

总线统一接收 CPU 的 32 位读写请求，并按物理地址分发到对应设备。当前主要地址映射为：

- 主内存：`[0, MEMORY_SIZE)`
- `Timer`：`0x1FE00100`
- `Uart`：`0x1FE001E0`
- `TestDevice`：`0x1FFFF000`

Bus 的引入把 CPU 与具体设备解耦，使平台可扩展，也方便在测试环境中插入新的 MMIO 设备。

### 8.2 UART

UART 是一个极简控制台输出设备，当前实现特征为：

- 基址：`0x1FE001E0`
- 空间大小：4 字节；
- 偏移 0 写入时，取低 8 位作为字符输出到终端；
- 当前不支持输入，`read32()` 恒返回 0。

这种设计足以支撑程序打印调试信息和基础字符输出，同时保持了 MMIO 设备模型的清晰性。

### 8.3 Timer

Timer 提供定时计数和中断挂起能力，包含：

- `TVAL`：当前计数值；
- `TCFG`：阈值配置；
- `TCTL`：使能控制；
- `TCLR`：中断清除。

当计数达到阈值周期后，Timer 会置位挂起中断，等待 CPU 处理。这个模块让平台不再是“只有 CPU 和内存”的静态系统，而具备了基础中断驱动能力。

### 8.4 TestDevice

TestDevice 是测试框架中最关键的 MMIO 设备，用于承接 goodtrap/badtrap 协议：

- 向 `0x1FFFF000` 写入 `0`：代表 `goodtrap`，即程序通过；
- 向 `0x1FFFF000` 写入非 0：代表 `badtrap(code)`，即程序失败并携带退出码。

这个设计使得测试程序无需依赖操作系统，只需向一个固定 MMIO 地址写值，就能把“测试是否通过”的结果传递给模拟器外层框架。

## 9. 测试框架搭建

### 9.1 测试框架的整体目标

项目的测试体系不是单一层次的，而是分为三层：

- 单元测试层：验证模块级行为；
- 程序级回归层：验证二进制样例程序是否能正确跑通；
- C 程序测试层：验证交叉编译后的实际 LoongArch 程序是否能在当前平台稳定运行。

这种分层结构让测试既能快速定位模块错误，也能覆盖更贴近真实应用的完整执行路径。

### 9.2 单元测试层

单元测试位于 `tests/unit/`，当前共有 18 个测试源文件，对应 18 个可执行测试程序。测试覆盖内容包括：

- CPU 基础行为与状态；
- 内存读写与越界；
- Bus 路由；
- UART 与 Timer；
- 程序加载器；
- 模拟器运行器；
- runtime/trap 协议；
- MMU 和分页；
- 分支、数组、load/store 等程序行为。

项目内置了一个轻量测试头 `tests/unit/test_framework.h`，通过以下宏组织断言：

- `EXPECT_TRUE`
- `EXPECT_EQ`
- `EXPECT_THROW`
- `TEST_PASS`

这种框架非常轻量，不依赖外部测试库，适合课程项目快速落地和调试。

### 9.3 程序级回归层

程序级回归由 `build/program_test_runner` 驱动，读取 `tests/program/program_test_manifest.txt`，逐条运行预置的 `.hex` 程序，并与期望退出码进行对比。

这一层的特点是：

- 直接运行二进制程序，而不是只测单条指令；
- 覆盖分支、数组、load/store、trap 等组合行为；
- 能在每次修改 CPU 核心后做快速回归。

当前默认程序回归清单共有 11 项，包括：

- `test_pass`
- `test_fail`
- `trap_pass`
- `trap_fail`
- `check_fail`
- `branch_pass`
- `branch_fail`
- `load_store_pass`
- `load_store_fail`
- `array_pass`
- `array_fail`

### 9.4 C 程序测试层

这一层是项目工程化价值非常高的一部分。流程如下：

1. 使用 `toolchain/build_c_program.sh` 调用 LoongArch 交叉编译器；
2. 将 `runtime/start.S`、`runtime/trap.c` 与目标 `*.c` 文件一起编译；
3. 通过 `runtime/linker.ld` 链接成 ELF；
4. 用 `objcopy` 生成 `build_runtime/*.bin`；
5. 用 `build/mycpu_sim` 运行并统计结果。

默认编译选项为：

- `-ffreestanding`
- `-nostdlib`
- `-nostartfiles`
- `-nodefaultlibs`
- `-O0`
- `-g`

这意味着测试环境完全建立在“裸机 + 最小运行时 + 自研模拟器”之上，能够更纯粹地暴露 CPU 和运行时层面的问题。

### 9.5 最小运行时与 trap 协议

`runtime/` 目录实现了最小 C 运行时，其职责包括：

- 设置程序入口；
- 提供基本 trap 与退出能力；
- 通过 MMIO 将程序返回值映射到测试设备。

协议约定如下：

- `main()` 返回 0：写 0 到 `0x1FFFF000`，表示通过；
- `main()` 返回非 0：写非 0 到 `0x1FFFF000`，表示失败；
- `check(cond)` 失败时触发 `badtrap(1)`。

这个约定使测试判定逻辑简洁、稳定，也便于与其他教学框架做口径统一。

## 10. 测试框架对齐工作

### 10.1 对齐工作的背景

除了“能测”，这个项目还进一步追求“可比较”。为此，仓库专门做了 LoongArch 与 PA `test_copy` 框架的对齐工作，目标是让两边在尽可能公平的口径下进行横向比较。

### 10.2 已完成的对齐内容

根据仓库中的对齐报告，当前已经完成的框架级对齐包括：

- 测试集合一致：双方都只跑 35 个 `test_copy` 程序；
- 测试顺序一致：manifest 顺序一一对应；
- compare 构建标准一致：均按 `-O0 -g` 构建；
- 主时间口径一致：都使用虚拟机内部执行段 `host time spent`；
- 汇总字段一致：统一输出 `status`、`host_time_us`、`host_time_ms`、`instructions`；
- compare 入口独立：保留旧入口的同时，新增 compare 专用入口。

LoongArch 侧新增或调整的关键点包括：

- `RunResult` 增加 `host_time_us`；
- `SimulatorRunner` 只对执行循环内部计时；
- `simulator_main` 固定输出 `host time spent` 和 `total guest instructions`；
- `run_c_tests.sh` 优先解析模拟器内部统计；
- 新增 compare 专用 manifest：`tests/program/c_test_copy_manifest.txt`；
- 新增 compare 入口：`toolchain/run_c_tests_compare.sh`。

### 10.3 对齐后的边界

需要特别强调的是，框架“对齐”并不等于工作负载“完全相同”。两边仍然存在不可消除的差异：

- ISA 不同：LoongArch32 与 RISC-V32；
- 编译器后端不同；
- runtime 不同；
- trap 与启动路径不同；
- guest 指令流天然不同。

因此，更准确的表述应当是：

> 当前已经完成的是“框架层面对齐”和“统计口径对齐”，而不是机器级执行内容的完全等价。

这一区分对于课程汇报非常重要，因为它决定了性能结论的解释方式是否严谨。

## 14. 补充实验一：LoongArch 与 RISC-V 运行时间对比分析

### 14.1 实验目的

这一组实验的目标不是简单比较“两边谁更快”，而是在测试框架已经完成对齐的前提下，分析 LoongArch 模拟器与 PA 中 RISC-V NEMU 在同一批 C 程序上的执行时间差异，并判断这种差异到底主要来自：

- 测试框架本身；
- 虚拟机执行热路径；
- ISA 与编译器代码生成差异；
- 个别程序的工作负载特征。

### 14.2 实验口径

本实验采用 compare 专用入口，双方都使用：

- 相同的 35 个 `test_copy` 程序；
- 相同的 `-O0 -g` 编译口径；
- 虚拟机内部执行段 `host time spent` 作为主评分时间；
- 相同的 `status`、`instructions` 等汇总字段。

因此，这组实验比较的是：

> 在框架口径已经对齐之后，LoongArch 最小运行时 + LoongArch 模拟器，与 RISC-V AM 运行时 + NEMU，在同一组 C 程序上的执行成本差异。

### 14.3 实验结果

#### 14.3.1 官方 compare 汇总结果

| 指标 | LoongArch | PA / RISC-V |
| --- | ---: | ---: |
| 通过数 | 35 / 35 | 35 / 35 |
| Scored time | 9.811 ms | 29.616 ms |
| Total time | 10818.285 ms | 23989.984 ms |

按官方 compare 汇总口径，PA / RISC-V 的主评分时间约为 LoongArch 的 `3.02x`。

#### 14.3.2 逐项重提取结果

在对 35 个程序逐项重新提取统计后，得到如下总和：

| 指标 | LoongArch | PA / RISC-V |
| --- | ---: | ---: |
| 汇总执行时间 | 9294 us | 29616 us |
| 汇总执行时间 | 9.294 ms | 29.616 ms |
| 汇总 guest 指令数 | 706136 | 283882 |

按逐项重提取口径，PA / RISC-V 的执行时间约为 LoongArch 的 `3.19x`。  
这一数值与官方 compare 的 `3.02x` 略有差别，原因是 `host time spent` 本身会受宿主机调度噪声影响，但两者都指向同一个结论：**在当前对齐口径下，LoongArch 整体更快。**

#### 14.3.3 关键现象

从逐项结果中可以看出三个最重要的现象：

1. 大多数程序中，PA / RISC-V 都比 LoongArch 慢。
2. 不是所有程序都是这样，`mersenne` 是最明显的反例。
3. 在一大批 guest 指令数几乎相同的程序中，PA 仍然明显更慢。

例如：

- `bubble-sort`：LoongArch `168 us`，PA `1615 us`
- `crc32`：LoongArch `455 us`，PA `4104 us`
- `matrix-mul`：LoongArch `731 us`，PA `6568 us`
- `pascal`：LoongArch `151 us`，PA `1115 us`

而 `mersenne` 则恰好相反：

- LoongArch：`5910 us`，`434629` 条 guest 指令
- PA：`1498 us`，`14679` 条 guest 指令

这说明 LoongArch 并不是对所有程序都绝对占优，而是**整体趋势占优、个别程序受代码生成和工作负载特征影响会出现反转**。

### 14.4 实验分析

#### 14.4.1 第一结论：测试框架已经不是主要变量

由于 compare 专用入口已经完成了测试集合、构建选项和时间口径的统一，因此当前结果不能再简单归因于“谁的脚本算得更快”。框架因素当然仍然存在，但它已经不再是当前对比结果的主要解释变量。

换句话说，这组实验首先证明的是：

> 当前的 LoongArch 与 PA 对比，已经从“框架不统一时的粗略比较”，进入了“框架基本对齐后的可分析比较”阶段。

#### 14.4.2 第二结论：LoongArch 更快的主因是每条 guest 指令的宿主机成本更低

在仓库已有分析中，抽出了 22 个 guest 指令数几乎相同的程序。对这些程序汇总后：

- LoongArch 总时间：`2316 us`
- PA 总时间：`19812 us`
- LoongArch 每条 guest 指令约 `12.21 ns`
- PA 每条 guest 指令约 `104.41 ns`

这组数据非常关键，因为它说明在“工作量几乎一样”的前提下，PA 仍然慢很多。由此可以推断：

> 当前 LoongArch 更快的最主要原因，不是它做了更少的事情，而是它在宿主机上执行每条 guest 指令时的固定成本更低。

这一点与两边模拟器的结构也能对应起来：

- LoongArch 模拟器更轻量，执行循环更短，设备模型更精简；
- NEMU 作为更完整的通用系统模拟器，每条指令后还要维护更多系统级逻辑。

#### 14.4.3 第三结论：ISA 与编译器代码生成是重要次因

LoongArch 与 RISC-V 的差异并不只体现在解释器热路径，还体现在：

- ISA 不同；
- 编译器后端不同；
- runtime 不同；
- trap 与启动路径不同。

这会直接影响生成出来的 guest 指令序列。`mersenne` 就是最典型的例子：LoongArch 在这一项中执行了远多于 PA 的 guest 指令，因此尽管 LoongArch 虚拟机更轻，最终总时间仍然被反超。

因此，第二层结论应当表述为：

> 当程序特征触发某种较差的 LoongArch 代码生成路径时，ISA 和编译器差异会从“次因”上升为“主因”，并改变最终时间结论。

### 14.5 实验结论

本实验可以得出以下结论：

1. 在 compare 框架完成对齐后，LoongArch 在这组 35 个 `test_copy` 基准上整体快于 PA 的 RISC-V NEMU。
2. 这一结论的主因不是测试框架，而是 LoongArch 模拟器每条 guest 指令的宿主机执行成本更低。
3. ISA、runtime 和编译器代码生成差异是重要次因，并在个别程序上决定最终结果。
4. 因此，“LoongArch 更快”是一个成立的总体结论，但它应被理解为当前实现和当前基准下的综合结果，而不是对所有程序和所有场景的绝对结论。

## 15. 补充实验二：LoongArch 基础版与提高版时间对比分析

### 15.1 实验目的

这一组实验的目标是比较同一个 LoongArch 平台中两种核心模式的差异：

- `baseline`：顺序执行基础版；
- `advanced`：带流水线、动态分支预测、保留站、寄存器重命名和 ROB 的提高版。

这组实验并不是为了证明“提高版一定更快”，而是为了回答两个问题：

1. 引入更复杂微结构后，系统在宿主机上的时间开销发生了什么变化？
2. 提高版是否真的产生了流水线化、动态调度和乱序执行的结构性证据？

### 15.2 实验口径

实验使用 `tests/program/c_test_copy_manifest.txt` 中的 35 个程序，分别在：

- `toolchain/mycpu_sim_baseline.sh`
- `toolchain/mycpu_sim_advanced.sh`

两种模式下运行，并统一使用模拟器输出的 `host time spent` 作为时间统计依据。

### 15.3 实验结果

#### 15.3.1 原框架汇总结果

| 指标 | baseline | advanced |
| --- | ---: | ---: |
| 通过数 | 35 / 35 | 35 / 35 |
| Scored time | 35.176 ms | 363.112 ms |
| Total time | 21198.350 ms | 13948.983 ms |

按原框架汇总口径，`advanced` 的主评分时间约为 `baseline` 的 `10.32x`。

#### 15.3.2 套件汇总结果

| 指标 | baseline | advanced |
| --- | ---: | ---: |
| 35 程序总宿主时间 | 38446 us | 364963 us |
| 总 guest 指令数 | 706136 | 706136 |
| 总 guest cycles | 706136 | 941745 |
| suite IPC | 1.0000 | 0.7498 |
| suite CPI | 1.0000 | 1.3337 |
| suite slowdown | 1.0000x | 9.4929x |

按逐项汇总口径，`advanced` 的宿主机执行时间约为 `baseline` 的 `9.49x`。  
与前一个实验一样，两组慢化倍数不完全相同，主要原因是宿主机测量噪声存在，但总体趋势完全一致：**提高版明显更慢。**

#### 15.3.3 提高版的微结构统计

尽管 `advanced` 更慢，但它也给出了非常明确的微结构证据：

- 加权分支预测准确率：`78.52%`
- 平均 ROB 占用：`18.74`
- 平均在飞指令数：`19.79`
- 总乱序完成次数：`233874`
- 总寄存器重命名次数：`558449`
- 总冲刷水线次数：`14694`
- 总投机清除次数：`135291`

这些统计说明，提高版并不是“看起来复杂一点的顺序核”，而是已经真实运行了：

- 分支预测；
- 指令窗口；
- 乱序完成；
- 顺序提交；
- 投机恢复。

### 15.4 实验分析

#### 15.4.1 第一结论：提高版更慢，不代表设计失败

从宿主机执行时间看，`advanced` 比 `baseline` 明显更慢，这是一个非常清楚的实验事实。但这个事实不能直接解读为“提高版 CPU 比基础版差”，原因在于：

- `baseline` 本质上是功能级顺序解释器；
- `advanced` 需要额外模拟 IF/ID、保留站、RAT、ROB、功能部件、预测器、刷流水线和恢复逻辑。

换句话说，`advanced` 慢的不是 guest 程序本身，而是**宿主机为了模拟更真实、更复杂的微结构，做了大量额外工作**。

因此，本实验的第一层结论是：

> 提高版的主要代价，是模拟复杂微结构本身带来的解释器开销，而不是程序工作量增加。

#### 15.4.2 第二结论：提高版的价值在“微结构能力升级”，不在“解释器提速”

虽然 `advanced` 在宿主机时间上更慢，但从统计结果可以明确看出：

- 它存在有效的分支预测；
- 它存在稳定的 ROB/RS 占用；
- 它存在大量重命名和乱序完成；
- 它存在明确的投机执行与失预测恢复。

这说明 `advanced` 达成的核心成果是：

> 把 CPU 从一个顺序功能模型，升级成了一个带有现代处理器关键机制的微结构实验模型。

对课程实验而言，这一点比“宿主机更快”更重要，因为它使得该项目具备了讨论流水线、动态调度和乱序执行的真实基础。

#### 15.4.3 第三结论：提高版的 guest cycle 更高，是当前模型下的合理结果

在统计中可以看到：

- `baseline` 总 guest cycles：`706136`
- `advanced` 总 guest cycles：`941745`

这说明在当前模型下，提高版的周期数也更高。原因主要包括：

- 分支失预测会引起刷流水线；
- ROB/RS 容量有限，会引起停顿；
- 访存顺序和 Load/Store 相关性会带来等待；
- 功能部件是单实例，无法做到真正多发射。

因此，当前提高版并不是一个“理想加速器”，而是一个“带真实约束与真实惩罚的微结构模型”。这也正是它更适合作为课程实验平台的原因。

### 15.5 实验结论

本实验可以得出以下结论：

1. 在当前实现下，LoongArch 提高版在宿主机执行时间上明显慢于基础版，慢化倍数约为 `9.5x` 到 `10.3x`。
2. 这种变慢的主要原因，是提高版引入了大量微结构状态与调度逻辑，导致解释器模拟成本大幅增加。
3. 但提高版的真正价值并不在于宿主机时间更短，而在于它成功实现了流水线、分支预测、动态调度、重命名、乱序完成和顺序提交等关键机制。
4. 因此，从实验目的来看，提高版是一次“微结构能力增强实验”，而不是一次“解释器性能优化实验”。

## 16. 两组补充实验的综合结论

将上述两组实验放在一起看，可以得到更完整的课程结论。

第一，LoongArch 与 RISC-V 的 compare 实验说明：在框架对齐后，LoongArch 当前实现整体上具有更低的宿主机执行成本，这主要体现了虚拟机执行热路径更轻、更定制化的优势。

第二，LoongArch 基础版与提高版的对比实验说明：引入更高级的微结构并不会自动让模拟器在宿主机上更快，但它显著提升了 CPU 模型的体系结构表达能力和实验研究价值。

第三，这两组实验结合起来，恰好从两个方向说明了本项目的意义：

- 从“横向对比”看，它具有较好的工程实现效率；
- 从“纵向演进”看，它完成了从顺序模型到高级微结构模型的清晰升级。

因此，可以把本项目的最终定位概括为：

> 这不是一个只追求跑分的模拟器，而是一套兼顾体系结构正确性、微结构可研究性和测试工程化能力的 LoongArch 教学 CPU 实验平台。
